# 实战执行模式（从真实项目提炼）

> 本文档的模式不是理论，是从 `multiplatform-content-pipeline`（原股票知识库）等真实项目的 `docs/project-management/` 体系中提炼的可复用做法。
> 适用场景：项目已经启动、进入执行阶段，需要一套"能跑起来"的轻量治理机制。
> 与其他模块的关系：initiate 管"怎么开工"，monitor 管"怎么不跑偏"，本文档管"执行层面的具体机制怎么搭"。

---

## 一、工程记忆体系（project-memory bundle）

### 解决什么问题

每次新对话 AI 都要重新理解项目架构、踩过的坑、关键技术决策——重复问、重复查、容易遗漏。ADR 记录了"决策是什么"，但散落在多个文档里，新会话找不到入口。

### 怎么做

在项目 `docs/project-management/memory/` 下建一个轻量记忆 bundle：

```
docs/project-management/memory/
├── index.md              # 记忆入口（有什么、在哪、按领域分类）
└── concepts/             # 概念文档（每个是"结论+指针"，不复制原文）
    ├── architecture-xxx.md
    ├── workflow-xxx.md
    └── standard-xxx.md
```

### index.md 的写法

```markdown
# 工程记忆 bundle

> 新会话恢复顺序：根 AGENTS.md（规则）→ 本页 index（有什么、在哪）
> → 按需沿每篇的「来源与下钻」深读原始文档。
> 本 bundle 只做"结论 + 指针"，不复制、不替代原文。
> 易变状态（进度、计数、当天日期）不进本 bundle，需要时实时读台账。

# 架构（Architecture）
* [多平台内容流水线架构](concepts/architecture-pipeline.md) - 五层架构、平台插件化、行业隔离（ADR-004）
* [四地存储分工与仓库版图](concepts/architecture-storage.md) - Git/本地/网盘/飞书各放什么

# 链路（Workflow）
* [视频号采集链路](concepts/workflow-video-capture.md) - MITM捕获→下载→解密→验证
* [转写与OCR链路](concepts/workflow-transcription.md) - FunASR本地转写、Vision OCR

# 治理（Standard）
* [证书与代理核心规则](concepts/standard-cert-proxy.md) - 证书路径坑、全网阻断紧急恢复
* [故障排查先验顺序](concepts/standard-debugging.md) - 九成失败是自身问题、凭证最后怀疑
```

### concept 文档的写法

每个 concept 文档 50-150 行，结构固定：
1. **一句话结论**（这个概念的核心是什么）
2. **关键细节**（3-5 条要点，带数字和具体做法）
3. **来源与下钻**（指向 ADR / SOP / 代码的具体路径，不复制正文）
4. **常见坑**（2-3 条踩过的坑和规避方法）

### 维护规则

- **只增不删**：概念过时了加"[已退役 YYYY-MM-DD：原因]"，不硬删
- **问题驱动更新**：发现记忆和实际不符，当场更新
- **不抄易变计数**：已下载多少、已转写多少以现场文件为准，不写进记忆
- **稳定结论指针化**：过程件只放指针指向 ADR/记忆，不复制结论正文

## 二、活跃任务管理（active/）

### 解决什么问题

项目做着做着不知道"现在做到哪了、下一步是什么、有什么卡住了"。TODO 散落在对话里、脑子里、便签里，没有一个唯一真相源。

### 怎么做

在项目根目录建 `project-management/active/`，放两个动态文件：

```
project-management/active/
├── TASK_STATUS.md    # 任务状态台账（当前做什么、到哪）
└── ISSUES.md         # 问题清单（开放问题、已解决、做不通的方向）
```

### TASK_STATUS.md 的结构

```markdown
# 任务状态台账

> 本页是"当前做什么、到哪"的唯一进度真相，实时更新。
> 需求溯源看 docs/REQUIREMENTS.md，开放缺陷看 ISSUES.md。
> 稳定技术结论的权威版在 ADR / 工程记忆，本页只放指针、不复制结论。

## 依赖与并行前沿
- **阶段1**：✅ 完成（commit xxx）
- **阶段2**：⏳ 进行中
- **阶段3**：📋 待启动
- 可并行：A（后台运行）与 B（前台开发）可同时进行

## 工单清单

| 编号 | 标题 | 类型 | 前置 | 状态 | 验收 / 落点 |
|------|------|------|------|------|------------|
| T-01 | xxx | feature | 无 | done | 产出物路径 |
| T-02 | xxx | feature | T-01 | doing | 预期产出 |
| T-03 | xxx | bugfix | 无 | blocked | 阻塞原因 |
| T-04 | xxx | refactor | 无 | todo | 预期产出 |

状态四档：todo / doing / blocked / done

## 关键口径（指针，不展开）
- **技术点A**：结论一句话 → 见工程记忆 concepts/xxx
- **技术点B**：结论一句话 → 见 ADR-002

## 下一步（按优先级）
1. 最高优先级任务（T-xx）
2. 次优先级任务（T-xx）
3. 可后台运行的任务（T-xx）
```

### ISSUES.md 的结构

```markdown
# 问题清单

## 开放问题（Open）

### ISSUE-001: 问题标题
- **状态**：待启动 / 研究中 / 修复中
- **发现时间**：YYYY-MM-DD
- **问题描述**：具体现象、影响范围
- **根因**：（找到后填写）
- **方案**：（确定后填写）
- **验证**：（修复后填写验证方法和结果）

## 已解决问题（Closed）
### ISSUE-00x: 问题标题 ✅
- **解决时间**：YYYY-MM-DD
- **根因**：一句话
- **方案**：一句话

## 已验证做不通的方向（Won't Fix）
- 方向A → 原因（什么情况下试过、结果是什么）
- 方向B → 原因
```

### 维护规则

- **TASK_STATUS 必须立即更新的场景**：任务开始时、每个子任务完成时、任务完成时、遇到阻塞时、项目结构重大变更时、每次 git 提交前
- **ISSUES 发现即记录**：不要等"攒够了再写"，发现问题当场记录，解决后当场标注
- **Won't Fix 很有价值**：记录"做不通的方向"可以避免后来人（包括未来的自己）重复踩坑
- **不抄易变计数**：已完成多少个以现场成品文件为准，不写进台账

## 三、批量任务执行规范

### 解决什么问题

批量处理 100 个视频、500 篇文章时，跑到一半崩了，不知道哪些做完了、哪些失败了、从哪继续。没有断点续传机制，每次都从头来。

### 触发条件（满足任一即必须建批次状态）

1. 批量处理 >3 个同类项目
2. 预计执行时间 >1 小时
3. 涉及多个工具链（捕获+下载+处理+验证）
4. 用户明确要求"批量处理""全部完成"

### 三层状态记录

| 层级 | 位置 | 内容 |
|------|------|------|
| 批次明细 | `workspace/state/` | 具体进度、断点、锁文件（不入库） |
| 指针级状态 | `project-management/active/TASK_STATUS.md` | 只更新工单状态，不抄批次明细 |
| 问题记录 | `project-management/active/ISSUES.md` | 机制级问题（换平台还会踩的） |

### 批次状态文件（JSON）

```json
{
  "batch_id": "capture_20260915_001",
  "task_type": "video_download",
  "started_at": "2026-09-15T10:00:00+08:00",
  "updated_at": "2026-09-15T10:30:00+08:00",
  "status": "running",
  "total": 313,
  "completed": 150,
  "failed": 2,
  "skipped": 0,
  "current_item": "item_150_xxx",
  "failed_items": [
    {"name": "item_023_xxx", "reason": "下载超时", "retry_count": 3}
  ]
}
```

### 进度文件（JSONL，增量写入）

```
{"time": "2026-09-15T10:01:00", "action": "start", "item": "item_001"}
{"time": "2026-09-15T10:02:00", "action": "complete", "item": "item_001", "duration": 45}
{"time": "2026-09-15T10:03:00", "action": "fail", "item": "item_002", "reason": "timeout"}
```

### 锁文件机制

- 位置：`workspace/state/<task_type>.lock`
- 内容：PID + 启动时间
- 作用：防止多进程冲突
- 任务完成后必须删除锁文件

### 异常恢复流程

1. **中断检测**：检查锁文件是否存在 → 检查锁文件中的 PID 是否还在运行 → PID 不存在但锁文件存在 = 异常中断
2. **恢复步骤**：读取批次状态文件 → 从断点继续（跳过已完成项）→ 重试失败项（最多3次）→ 更新状态文件
3. **紧急清理**：异常退出后必须清理残留锁文件和系统代理状态

### 性能与资源保护

- 单次批次不超过 500 个项目（超过则分批）
- 下载并发数不超过 5（避免触发风控）
- 资源密集型任务（转写/编译）单进程运行
- 每处理 50 个项目保存一次状态（防止崩溃丢失进度）
- 失败项最多重试 3 次，超过则记录到失败清单

### 完成标准 Checklist

- [ ] 所有项目都已处理（总数 = 已完成 + 已跳过）
- [ ] 失败项有明确原因记录
- [ ] 状态文件已更新为"完成"
- [ ] 锁文件已删除
- [ ] TASK_STATUS.md 已更新
- [ ] 临时文件已清理
- [ ] 按文档同步检查清单同步相关文档

## 四、文档同步检查清单

### 解决什么问题

项目做着做着，文档和实际代码/结构脱节了——README 还写着旧目录、文档地图里有失效链接、新增的脚本没人知道在哪。每次 git 提交前没有统一检查，导致文档越来越不可信。

### 同步时机（必须执行的场景）

1. 完成采集/处理批次后
2. 发现问题并解决后
3. 项目结构调整后（新增/删除/移动目录或文件）
4. 大阶段完成后
5. 每次 git 提交前

### 六大检查项

#### 一、任务状态同步
- [ ] TASK_STATUS.md 已更新（工单状态正确、"下一步"已更新）
- [ ] ISSUES.md 已更新（新问题已记录、已解决问题已标注、机制级问题已提炼）

#### 二、文档关联同步
- [ ] DOCUMENTATION_MAP.md（文档地图）已更新（新增文档已加入、删除文档已移除、链接有效）
- [ ] WORKFLOW.md 已更新（如流程变更，阶段校验门正确）
- [ ] REQUIREMENTS.md 已更新（如需求变更，已关闭方案已加入"被取代"章节）

#### 三、目录结构同步
- [ ] DIRECTORY_STRUCTURE.md 已更新（新增目录已记录、删除目录已移除、存储分工说明正确）
- [ ] .gitignore 已检查（新文件类型已添加、不该入库的文件已忽略、git status 确认没有不该提交的文件）

#### 四、工具与脚本同步
- [ ] 新增脚本已加入文档地图「工具清单」
- [ ] 删除脚本已从文档中移除引用
- [ ] 脚本参数变更已更新到对应 SOP

#### 五、工程记忆同步（如稳定结论变更）
- [ ] memory/index.md 已更新
- [ ] 相关 concept 已修订
- [ ] 变更已记录

#### 六、ADR 决策记录（如重要决策）
- [ ] 重要决策已记录到 decisions/ADR-xxx.md
- [ ] 决策状态正确（已采纳/已废弃/提议中）

### 快速检查命令

```bash
# 检查 git 状态，确认没有不该提交的文件
git status

# 检查文档中是否有失效占位
grep -r "TODO\|待补充\|待完善" docs/ project-management/ AGENTS.md README.md

# 检查空目录
find . -type d -empty -not -path "./.git/*"
```

### 同步原则

1. **问题驱动更新**：发现问题立即评估是否需要更新文档
2. **本地文档为主**：所有文档以本地为准，飞书等外部文档为辅
3. **不抄易变计数**：已完成多少以现场成品为准，不抄进文档
4. **稳定结论指针化**：过程件只放指针指向 ADR/记忆，不复制结论正文
5. **提交前必查**：每次 git 提交前必须跑一遍本清单

## 五、存储分工硬约束

### 解决什么问题

什么东西该进 git、什么只放本地、什么上网盘、什么发飞书——没有明确分工，结果是 git 仓库塞满了视频和转写稿（几 GB），或者本地唯一一份原始素材被误删。

### 四地分工

| 位置 | 放什么 | 不放什么 |
|------|--------|----------|
| **Git 公有仓** | 代码、docs/、知识成品（清洗后）、台账元数据、ADR/工程记忆 | 媒体文件（视频/音频）、逐字转写稿、原文、凭证、过程件、临时文件 |
| **本地桌面项目** | 原始资源 + 知识成品（唯一权威源） | — |
| **百度网盘** | 成品镜像（备份） | 过程件、临时文件 |
| **飞书** | 暂缓；将来只发成品（不发过程件和原始素材） | — |

### 硬规则

1. **git status 是红线**：提交前必须检查，视频/音频/转写稿/凭证绝对不能进 git
2. **本地是唯一权威源**：网盘和飞书都是镜像/分发，本地丢了才是真丢了
3. **知识成品才入库**：只有"自己话重组、带来源、清洗后"的成品才进 git 的 knowledge/ 目录；原始素材（视频、逐字转写、原文）只在本地
4. **凭证单独管理**：`.secrets/` 目录必须在 .gitignore 里，加密存储，不入库

## 六、数据层编号体系（内容类项目）

### 解决什么问题

素材库目录乱——视频和转写稿混在一起、原始素材和知识成品分不清、新会话不知道"处理到哪一步了"。

### 按处理阶段编号

```
library/
├── 00_manifest/        # 台账（manifest、水位、队列、批次状态）
├── 01_video/           # 原片（按平台/账号分目录）
├── 02_audio/           # 音频（过程件，从视频提取）
├── 04_transcript/      # 逐字转写（原料，不入库）
├── 05_knowledge/       # 知识成品（清洗后，入库）
│   └── concepts/
│       ├── videos/     # 视频笔记
│       ├── articles/   # 图文笔记
│       ├── books/      # 书籍笔记
│       ├── reports/    # 报告笔记
│       ├── methods/    # 方法笔记
│       └── topics/     # 主题融合页
├── 06_articles/        # 图文原文（原料，不入库）
├── 07_books/           # 书籍
└── 08_sources/         # 平台无关外部源
```

### 编号原则

- **数字前缀 = 处理阶段**：00 台账 → 01 原始 → 02/04 中间件 → 05 成品 → 06/07/08 其他原料
- **跳号留扩展空间**：03 留空，将来可以插新的中间阶段
- **原料 vs 成品**：01/02/04/06/07 是原料（不进 git），05 是成品（进 git），00 是台账元数据（进 git）
- **按平台/账号分子目录**：01_video/bilibili/账号名/、04_transcript/douyin/账号名/

## 七、项目级 AGENTS.md

### 解决什么问题

每个项目都有自己的"怎么干活"规则（目录约定、工具用法、禁止事项），但这些规则散落在对话里、README 里、脑子里。新会话的 AI 不知道这个项目的特殊约定，容易犯"通用做法但本项目不行"的错误。

### 怎么做

每个项目根目录放一个 `AGENTS.md`，和 `README.md` 分离：

| 文件 | 给谁看 | 写法 |
|------|--------|------|
| README.md | 人 | 项目概览、目标、架构、快速开始（描述性） |
| AGENTS.md | AI | 操作手册、命令式、可执行、禁止事项、路径约定（指令性） |

### AGENTS.md 的核心内容

1. **项目定位与边界**：这个项目做什么、不做什么
2. **目录约定**：什么东西放哪、硬编码路径禁止、用 `$HOME` 还是相对路径
3. **工具用法**：本项目用什么工具、怎么调用、有什么坑
4. **禁止事项**：绝对不能做的事（如"不要修改 data/ 下的原始素材"）
5. **新会话恢复顺序**：先读什么、再读什么（AGENTS → DOCUMENTATION_MAP → memory/index → TASK_STATUS）
6. **提交前检查**：git 提交前必须跑的检查清单

### 与全局 AGENTS.md 的关系

- `~/Doubao/AGENTS.md` 是全局规则（所有项目通用）
- 项目根目录的 `AGENTS.md` 是项目特有规则（仅该项目内优先）
- 冲突时：项目 AGENTS.md > 全局 AGENTS.md

## 八、评审改进批次机制

### 解决什么问题

评审发现了 20 个问题，一股脑全改容易乱、容易漏、不知道改到哪了。没有优先级，先改哪个后改哪个全凭感觉。

### 怎么做

评审后按优先级分批次改进，每批次一个工单：

```
评审 → 问题清单（按 P0/P1/P2/P3 分级）
     → 批次1（P0，最紧急）→ 工单 T-xx → 完成 → commit
     → 批次2（P1，重要）  → 工单 T-xx → 完成 → commit
     → 批次3（P2，一般）  → 工单 T-xx → 完成 → commit
     → 批次4（P3，可选）  → 工单 T-xx → 完成 → commit
```

### 批次记录格式

在 TASK_STATUS.md 中记录：

| 批次 | 工单 | 内容 | 优先级 | 完成 commit |
|------|------|------|:---:|:---:|
| 批次1 | T-24 | 清理与修正：删旧脚本+修数量+更新状态 | P0 | `<commit短哈希>` |
| 批次2 | T-25 | 文档精简：退役过时文档+修复 .gitignore | P1 | `<commit短哈希>` |

### 评审核心结论记录

评审文档末尾必须记录：
- **总体评分**（如 ⭐⭐⭐½）
- **方向判断**（架构方向是否正确）
- **核心问题**（最需要改进的 3-5 个问题）
- **改进批次**（按优先级分的批次清单）

## 九、模式选用指南

| 项目规模 | 建议启用的模式 |
|----------|---------------|
| 小项目（1-2周，单线程） | TASK_STATUS + ISSUES 即可，其他可选 |
| 中项目（1-3月，多任务并行） | + 工程记忆 + 文档同步检查清单 + 存储分工 |
| 大项目（3月+，批量处理，多平台） | + 批量任务执行规范 + 数据层编号体系 + 评审改进批次 |
| 所有项目 | 项目级 AGENTS.md（强烈建议，成本低收益高） |

**原则**：不要一上来就把所有模式都搭起来。从 TASK_STATUS + ISSUES 开始，项目长大到需要时再加。每个模式启用时，在 TASK_STATUS 中记录"已启用 XX 模式"。
