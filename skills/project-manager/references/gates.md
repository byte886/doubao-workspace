# L3 · gates 阶段门评审（Phase-Gate Review）

> 最后更新：2026-09-15
> 回答的问题：**"项目到节点了，继续往下走，还是卡住/砍掉？"**
> 对应专业方法：**Phase-Gate / Stage-Gate** 方法论——在阶段之间设检查点，做 Go/Conditional/Hold/Kill 决策。

## 阶段门到底是什么

在项目不同阶段之间设"检查点"，像收费站一样——到点必须停车，回答"继续往下走，还是先卡住/砍掉"。**不是汇报会，是真决策。**

最常见的失败：**门标准模糊**。标准不明确，门就变成"团队汇报、评审会点头、项目继续"的社交活动，什么都没真正评估。

> 来源：https://onplana.com/blog/stage-gate-project-management-onplana

## 为什么门标准必须二元化

门标准要写成**判断题**（是/否），不能写成**讨论题**。

- ❌ 模糊标准（= 社交活动）："看看我们进展怎么样？""感觉还行？"
- ✅ 二元标准（= 真决策）："更新后财务模型 NPV 是否 > $X？""最小原型是否获得 ≥ 10 个真实用户？"

模糊标准的门，100% 会变成"汇报完就继续"。

## 有效门标准的 5 个领域

| 领域 | 问什么 |
|---|---|
| 战略对齐 | 项目是否仍支持当前优先级？ |
| 财务健康 | 是否在预算内？完工预测是否可信？ |
| 进度绩效 | 是否按计划交付？偏差是否被主动管理？ |
| 风险状态 | 新风险是否出现？已有风险是否在缓解？ |
| 交付物与合规 | 本阶段交付物是否完成？是否符合标准？ |

> 来源：https://projectmanagementformula.com/phase-gate-process/

## 个人项目三道门（轻量版）

企业级 4-5 道正式门，个人场景压成三道：

```
G1 立项门 ──→ G2 验证门 ──→ G3 发布门
值不值得做？    最小验证成立吗？   达到上线标准了吗？
```

### G1 立项门：值不值得做？

**二元判断题**：
- [ ] 战略对齐 ≥ 3 分？
- [ ] 成功标准可量化？
- [ ] 活跃项目数没超 7±2？

任一否 → 不启动。

### G2 验证门：最小验证是否证明假设成立？

**二元判断题**（按项目类型替换）：
- 产品类：[ ] 最小原型获得 ≥ X 个真实用户/付费？
- 内容类：[ ] 一篇样稿达到流量/互动标准？
- 调研类：[ ] 主报告结论站得住，底稿已归档？
- 学习类：[ ] 用 2-3 章验证学习方法有效？

不通过 → Hold 或 Kill，不要硬推到 G3。

### G3 发布门：是否达到上线/交付标准？

**二元判断题**：
- [ ] 交付物完成并存入 `01_结论与产出/`？
- [ ] 剩余问题清单已明确列出？
- [ ] 上线/交付后维护责任已指定？

> 来源：https://projectmanagementformula.com/phase-gate-template/

## 门决策四分类

| 决策 | 含义 | 个人场景动作 |
|---|---|---|
| **Go（通过）** | 进入下一阶段 | 继续推进，更新总纲 |
| **Conditional Go（带条件通过）** | 满足条件后进入下一阶段 | 条件必须具体、可测量、有 owner、有截止日 |
| **Hold（卡住）** | 暂停，等条件解除 | 项目改 On Hold，定期回看 |
| **Kill（砍掉）** | 终止项目 | 走 close.md 退役流程 |

> **Conditional Go 的条件必须具体可测量 + 有 owner + 截止日**——模糊条件等于没条件。例：
> - ❌ 模糊："再优化一下 SEO"
> - ✅ 具体："在 2026-10-01 前完成 20 篇长尾词文章，由我负责"

> 来源：https://projectmanagementformula.com/phase-gate-template/

## 批量评审议程模板（每季度一次）

不要每个项目单独开门——**批量评审**，每季度一次，每个项目 3 分钟：

```
季度阶段门评审 · YYYY-QN
─────────────────────────────

1. 每个项目 3 分钟（轮流）：
   - 当前在哪个门？（G1/G2/G3 之间）
   - 本阶段交付物完成了吗？
   - 上一门遗留问题关闭了吗？

2. 每个项目给门决策：
   - Go / Conditional Go / Hold / Kill
   - Conditional Go 的条件写清楚（具体+owner+截止日）

3. 算总账：
   - 活跃项目数是否回到 ≤ 7？
   - 哪些项目转 On Hold / Kill？
   - 下次评审日期？
```

> 纯数字排序很少奏效——评分模型必须配一次"人来辩论"。批量评审就是这个"辩论会"。
> 来源：https://ones.com/blog/project-portfolio-management-explained-key-concepts-and-workflows/

## 评审 Checklist（过门前必过）

- [ ] 本阶段所有交付物完成
- [ ] 上一门遗留问题已关闭，或正式延期（附理由）
- [ ] 关键文档存入项目系统（01_结论与产出/ 或 09_调研底稿与素材/）
- [ ] 风险登记册是最近两周内更新的
- [ ] 进度/预算偏差已明确评估（若显著超支/延期，必须明确决定继续，而非默认会自己好）

> 来源：https://www.arcturuspro.com/blog/phase-gate-review-checklist

## KPI（可选，个人场景一般不用）

企业阶段门会跟踪两类指标：
- **Leading（前瞻）**：已完成客户访谈数、试点转化率、实验速度、证据强度分。
- **Lagging（滞后）**：阶段通过率、淘汰率、在某阶段停留时间。

个人场景默认不跟踪，除非你想优化"从 G1 到 G3 的平均时长"。

> 来源：https://beefed.ai/zh/stage-gate-portfolio-governance

## 企业级重型 vs 个人轻量对照

| 主题 | 企业级重型 | 个人轻量（推荐你用） |
|---|---|---|
| 门数量 | 4-5 道正式门 + 签字 | 3 道门（G1 立项 / G2 验证 / G3 发布） |
| 门标准 | 五领域全套指标 | 二元判断题（3-5 条） |
| 评审频率 | 每门一次正式评审会 | 季度批量评审，每项目 3 分钟 |
| KPI | Leading + Lagging 指标跟踪 | 默认不跟踪 |
| 决策记录 | 决策者签字 + 正式归档 | 一页门决策记录 |

## 反模式

- 门标准写成讨论题 → 门变成汇报会，什么都没真评估。
- Conditional Go 的条件模糊（"再优化一下"）→ 等于没条件。
- 每个项目单独开门 → 一年开 12 次会，累且没用。
- 过门前不查上一门遗留 → 老问题一直拖着。
- G2 验证门不认真过 → 没验证假设就硬推到 G3，上线即失败。
