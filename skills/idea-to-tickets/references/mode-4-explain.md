# 模式 4 · explain 视图讲清楚（上游 show-me）

> 目标：为"展示代码 / 改动 / 方案"建立选择标准——用**最小的、与问题匹配的视图**把关键点讲清楚，让人和 Coding Agent 的沟通具象、可评审。定位是"**一份展示 diff 的风格指南**"。
> 出处：上游 show-me 由 **humanlayer/skills** 出品（组件树 / 调用栈 / Mermaid 状态与时序 / 文件树），被 Matt Pocock 公开推荐；它与 clarify/spec/slice 不同源（那三个来自 mattpocock/skills）。

## 唯一核心原则
**选择能把关键点讲清楚的最小可视化视图。** 不是图越大越复杂越好，而是"刚刚好"。先理解当前任务，再判断画什么、怎么画、画到什么程度。

## 问题 → 视图 选型表
| 要讲清的东西 | 选用视图 | 说明 |
|---|---|---|
| 逻辑 / 分支判断 | 流程图（或伪代码式流程） | 判断条件、分支、返回结果一图看清，便于 review |
| 运行时执行过程 | 调用树 call tree | 从入口起，各环节先后与父子关系 |
| UI / 组件归属 | 组件树 component tree | 组件归属、谁给谁提供状态 |
| 模块 / 文件重构 | 树形 diff（文件树） | 目录增删、文件拆分、职责迁移同一视图 |
| 系统 / 模块交互 | 时序图 / Mermaid | 多对象消息往来、取消/状态变更 |
| 以上都不够的复杂拓扑 | 专门一张 HTML（或架构图） | 多入口、多变体、共享沙箱、策略引擎等层级关系 |

## 三条表达规则
1. **视图类型必须匹配问题**（别用炫技的复杂图讲一个简单分支）。
2. **只保留当前讨论需要的结构**，无关模块不画。
3. **图放在它所支撑的那段文字旁边**，图文对应。

## 渲染后端是可替换插槽（重要：不要重复造画图器）
本模式只产出"**画什么、什么类型、标注哪些关键节点、裁剪到什么程度**"的规格，真正渲染交给环境里的工具：
- **在豆包**：把视图规格交给内置 **doubao-visualization** 技能渲染（ECharts / HTML-SVG / 信息图），由它负责配色、可读性、移动端、降级；本模式不再生成一套渲染器。
- **在 Claude Code / Cursor / Codex**：直接输出 **Mermaid**（flowchart/sequenceDiagram 等）或独立 HTML 文件。
- 判断重叠：explain 管"选图与裁剪"，doubao-visualization 管"把图画好"——**先选型、后渲染，二选一不重复**。

## 适用时刻
- 代码评审 / 写 MR(PR) 描述：跨多文件、上千行改动压缩成一张时序/文件树。
- clarify/spec 时讲清现有机制；slice 后讲清工单将怎么动。
- 给他人（或下个会话的自己）交接一块复杂逻辑。

## 反模式
- 简单逻辑也上复杂大图、把无关模块全画进去。
- 图和说明分离、读者要来回找对应关系。
- 在豆包里另写一套图表代码而不走 doubao-visualization（重复建设）。
