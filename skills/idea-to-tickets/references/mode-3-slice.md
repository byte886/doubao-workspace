# 模式 3 · slice 垂直拆工单（上游 to-tickets）

> 目标：spec 是"一个想法的完整表达"，但**不是工作单元**。本模式把它拆成一张张**能单独开工、单独验收**的工单，标好依赖，排到可并行状态。

## 为什么不拆会坏
把装着五六件事的整份 spec 一次交给 Agent：①做到一半上下文塞满，留下改了一半、前后没接上的代码库；②跑很久回来说"做完了"，你无法验收、只能通读代码猜；③无法并行，互不相干的事被排成一队。

## 执行 SOP
1. **先读真实代码/材料再拆**（硬要求）：spec 写的是**意图**，代码里才是**真实情况**。常会发现 spec 没写、但必须先做的事（例：过滤规则早就存在，只是 57 篇里 55 篇没打标记导致规则空转——于是拆出 9 张而非 spec 数出来的 6 张）。
2. **按功能纵向切（垂直切片），不按层横切**（见下）。
3. **标注工单间真实依赖**，得到可并行的"前沿(frontier)"。
4. **发布前反向找用户确认三件事**（见下），确认后才落地。

## 垂直切片 / 曳光弹 tracer bullet（核心）
- 错误的"按层拆"：先写完所有测试→再改所有组件→最后统一样式。任一时间点都没有能拿出来看的东西。
- 正确的"按功能拆"：每张工单是**穿透所有层的一条细线**——改一点逻辑 + 加一条覆盖边界的测试 + 一个肉眼可见的变化，**做完即可见、即可验收**。一张工单 = 做成了一件事，不是改完一层。

## 依赖图是给并行 Agent 的调度信号
- 挂"阻塞/被阻塞"：无依赖的工单**立刻可并行**（同时开多个 Agent 各领一单、互不干扰；一张合并后依赖它的下一单自动就绪）。
- 分寸：**只标清晰、真实存在的依赖**。标少→两个 Agent 同时改同一块而撞车；标多→本可并行的被硬排成一队。"只是怕冲突"不算真实依赖。

## 两条实用规矩
1. **refactor 先行**：某改动很难落实时，先做一张"不改变任何行为"的工单——把模块抽出来、把地方腾出来。**先让改动变简单，再做那个简单的改动。**
2. **大范围重构是垂直切片的例外**：如给一个被几十处调用的接口改签名，天生横跨一整层，硬切竖片更糟。用**绞杀(strangler)三步**，三步三张工单、每步可单独合并、代码库全程可用：
   - 先加新的，让新旧并存；
   - 把调用方一批批迁到新接口；
   - 确认无调用后删掉旧的。

## 发布前三确认（机器出初稿，人来拍板）
1. 拆得对不对、太粗还是太细？（一张工单若混了"性质不同的两件事"——如改一小段逻辑 vs 批量补数据——要拆开；且补数据不改变行为，不应阻塞其它工单）
2. 依赖对不对？
3. 有没有该合并、或该再拆的？

## 落点适配（同一产物、两种读法，可平移）
- **任务系统模式**：一张工单一个 Issue，依赖用平台**原生阻塞字段**挂（会真的把被挡住的单标灰），适合多人/多 Agent。
- **本地文件模式**：建一个目录、一张工单一个文件、按依赖顺序编号（[`../templates/ticket.md`](../templates/ticket.md) + [`../templates/tickets-index.md`](../templates/tickets-index.md)），不联网、不污染任务列表，适合单人推进；随时可改发到任务系统。

## 一张工单应含
标题 / 目标（做成哪件"可见可验收"的事）/ 涉及层（逻辑·测试·界面）/ 验收标准（给定输入→期望结果）/ 依赖哪些工单 / 不属于本单（边界）。
