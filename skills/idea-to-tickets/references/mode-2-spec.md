# 模式 2 · spec 共识成规范（上游 to-spec）

> 目标：把 clarify 对齐、但只存在于对话里的共识，固化成一份**可交接、可验收**的规范文档。假设对齐已经完成，**不再反问需求**，只做整合与工程化。

## 为什么需要
不写 spec 直接开工的两种坏结果：①换新会话/换 Agent，对之前共识一无所知，从头解释；②凭模糊印象开工，没写下来的决策靠脑补、于是跑偏。**对齐最贵的不是达成，是达成后没被记下来。**

## 执行 SOP
1. **先扫代码库/现有材料，用项目自己的术语写**（不写脱离实际的空泛 PRD）。
2. **先找"接缝(seam)"再成文**（见下），必要时就接缝方案与用户确认一次。
3. 按 [`../templates/spec.md`](../templates/spec.md) 组织固定段落；每条行为写成**能验收的 user story**，而非"要好用/要好看"。
4. 明确写出"**不做什么**"，划清边界。
5. 产出后落盘：本地 md / 飞书 / 任务系统（落点可替换，见下）。

## 规范文档固定结构
- 问题是什么（现状与痛点）
- 方案是什么（选定方向）
- user stories：作为〈角色〉，在〈场景〉下，系统应〈可观测行为〉，以便〈价值〉——每条都能转成测试/验收
- 已定的实现决策（含放弃的备选及理由）
- 测试决策（在哪测、测什么边界）
- 不做什么（Out of scope）

## 接缝 seam（本模式最关键的工程思想）
写 spec 前先问：**这个功能要在哪测？**
- 逻辑散在界面组件里、和渲染缠在一起 → 无法单独测，要测就得渲染整页。
- 把逻辑抽成一个接口很小、背后藏全部逻辑的**独立纯函数/模块** → 只测它即可，这就是接缝。
- 规矩：**优先用已有的、层级最高的接缝；理想情况下整条改动只留一个。**
- 为什么 Agent 时代尤其重要：**好接口给测试一个耐久靶子**——接口稳定，底层被 Agent 改写多少遍测试都不用动，这是让 Agent 敢大胆改又不易出事的前提。

## 记决策，不记实现（硬纪律）
- **不写具体文件路径、不贴代码片段**：这些过时最快（今天写死路径，明天重构就全错）。
- spec 记"为什么这么定、要支持什么行为、边界在哪"，不记"第几行怎么写"。
- 易变值（进度、计数、日期、SHA）不抄进正文，放台账实时读。

## 落点适配（可平移插槽）
- 原生态：建 GitHub Issue 并打 `ready-for-agent`（可交给 Agent 直接实现）；一次性配置任务系统由其 setup skill 完成。
- 我们体系：**默认写成本地 md 规范**（用模板）；需要协作/排期再发飞书任务或任意 tracker。内容相同，只换存储。

## 与其它模式衔接
- 上游：clarify 的共识小结是输入。
- 下游：交给 slice 拆成工单；稳定、跨会话有价值的决策，同时按 **okf-wiki** 沉淀。
