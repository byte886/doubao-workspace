# 组合套路 Playbook：走哪档、怎么串、怎么避坑

## 1. 分档选用（不是每次都走全套）

| 档位 | 何时用 | 链路 | 产出 |
|---|---|---|---|
| **L0 直接做** | 需求无歧义、机械执行 | 无 | 结果 |
| **L1 只澄清** | 需求模糊、还没决定做不做/怎么做；选题与决策 | clarify | 共识小结 |
| **L2 澄清+固化** | 怕换会话失忆、要交接、要评审依据 | clarify → spec | 共识 + 带验收规范 |
| **L3 全链路拆单** | 多步骤大任务、要多 Agent/多会话并行 | clarify → spec → slice | 共识 + 规范 + 工单与依赖图 |
| **横向 explain** | 任一阶段需要讲清代码/改动 | explain（可随时插入） | 最小合适视图 |

判断：拿不准走几档时，**从 clarify 起步**，对齐后自然能判断要不要继续 spec/slice；别一上来就给简单任务套全流程。

## 2. 标准全链路（L3）步骤
1. **clarify**：先勘察材料 → 一次一问、先给推荐 → 出共识小结 → 用户确认。
2. **spec**：扫代码、找 seam → 写带 user story 与验收的规范、写明不做什么 → 记决策不记实现。
3. **slice**：再读真实代码 → 垂直切片拆单 → 标真实依赖、识别可并行前沿 → 发布前三确认 → 落本地/飞书/GitHub。
4. **实现与评审**（本技能之外）：工单交编程 Agent；explain 把改动讲清楚用于评审。
5. **记忆沉淀**：稳定决策/规范按 okf-wiki 存 concept/log，供跨会话恢复。

## 3. 常见反模式（对照纠偏）
- **没对齐就做**：跳过 clarify，AI 脑补用户没说的决策 → 返工。
- **达成不落盘**：只聊不写 spec，换会话全部蒸发。
- **按层横拆**：先做完全部测试再做完全部 UI，中途没有可看的东西、无法提前验收。
- **依赖乱标**：标少撞车、标多变串行；只标真实依赖。
- **spec 写死路径/贴代码**：重构即过期；只记决策与行为。
- **不读现状照 spec 拆**：意图≠现状，漏掉进门前必须先扫的地基工单。
- **一次发布不确认**：机器拆解只是初稿，粗细/依赖/合并必须人拍板。
- **小任务过度流程化**：L0 能解决的别硬走 L3。

## 4. 两个真实示例（来自上游演示，用于校准尺度）
- **博客首页改造**：clarify 问出"博客当主角 / 订阅放两处 / 大图锁定最新长文、其余降级"；spec 抽出纯函数接缝 `getHomepageContent`（页面只渲染其返回值），user story 含"只发早读没发长文时大图保持上一篇长文"；slice 发现 57 篇早读仅 2 篇带类型标记导致过滤空转，最终拆 9 张（比 spec 字面多 3 张地基单），并把混了"改逻辑+补数据"的首单再拆开。
- **非代码选题**：用 clarify 决定"下一期讲什么"——做哪个主题/给谁/多深/主线/开场，三问定案，留下可直接用的记录。

## 5. 平移到其它 IDE / Agent 的对照
| 环节 | 豆包 | Claude Code / Cursor / Codex |
|---|---|---|
| 触发 | 开场话术点名模式 | slash command：`/grill-me` `/to-spec` `/to-tickets` `/show-me` |
| 规范/工单落点 | 本地 md、飞书任务 | GitHub Issues（`ready-for-agent` 标签、原生阻塞关系） |
| 视图渲染 | doubao-visualization | Mermaid / 独立 HTML |
| 记忆 | okf-wiki | 项目 AGENTS.md / 决策日志 |

方法、判断标准、模板不变，只替换这四类后端。
